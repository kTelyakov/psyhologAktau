# Многоязычность: русский, казахский, английский

Статус: архитектурное решение на согласование. Код не писался.
Дата: 2026-11-03

---

## 1. Главное ограничение

Русские URL проиндексированы и дают весь текущий трафик:

```
psyholog-aktau.kz/blog/semja/izmenil-muzh-chto-delat/
```

**Их нельзя менять ни на символ.** Это диктует схему: русский остаётся
на корне без префикса, остальные языки получают префикс.

```
/blog/semja/izmenil-muzh-chto-delat/        ru  ← как было
/kk/blog/semja/izmenil-muzh-chto-delat/     kk
/en/blog/semja/izmenil-muzh-chto-delat/     en
```

Альтернативы и почему отклонены:

| Вариант | Почему нет |
|---|---|
| Поддомены `kk.psyholog-aktau.kz` | Авторитет домена делится между поддоменами, нужны отдельные подтверждения в вебмастерах |
| Параметр `?lang=kk` | Поисковики плохо индексируют, канонизация превращается в возню |
| Определение по IP/заголовку без URL | У каждого языка должен быть свой адрес, иначе его нечего индексировать |
| Префикс для всех, включая `/ru/` | Потеря всех текущих URL. Исключено |

## 2. Стек

**`next-intl`** — для App Router это фактический стандарт. Важно, что
он умеет `localePrefix: 'as-needed'`: ровно та схема, которая нужна —
дефолтный язык без префикса, остальные с префиксом.

```
npm i next-intl
```

Почему не альтернативы: `next-i18next` не поддерживает App Router,
самописное решение придётся самому стыковать с ISR, metadata
и статической генерацией.

## 3. Два разных вида перевода

Их нельзя смешивать — это главная развилка в архитектуре.

### 3.1 Интерфейс — файлы сообщений

Кнопки, заголовки секций, подписи полей, тексты ошибок.
Их немного (~150 строк), они меняются редко, переводятся один раз.

```
web/messages/
  ru.json
  kk.json
  en.json
```

```json
{
  "hero": {
    "badge": "Психолог в Актау · 20 лет практики",
    "cta": "Бесплатная консультация"
  },
  "blog": {
    "title": "Статьи психолога",
    "count": "{count, plural, one {# статья} few {# статьи} other {# статей}}"
  }
}
```

Склонения по числам next-intl берёт на себя через ICU —
самописный `postsPlural` после этого можно выбросить.

### 3.2 Контент — база данных

58 статей, 10 рубрик, тексты страниц услуг. Это не «строки
в интерфейсе», а контент, который будет редактироваться в админке.

**Схема: отдельные таблицы переводов.**

```
posts                        ← не зависит от языка
  id, slug, category_id, author_id, image,
  published_at, status, created_at, updated_at

post_translations            ← НОВАЯ
  id, post_id, locale,
  title, content, excerpt,
  meta_title, meta_description,
  status                     ← черновик перевода ≠ черновик статьи
  UNIQUE (post_id, locale)

categories
  id, slug, sort_order

category_translations        ← НОВАЯ
  id, category_id, locale, title, description
  UNIQUE (category_id, locale)
```

Почему так, а не колонкой `locale` в `posts`:

- связь между переводами одной статьи явная, а не через
  искусственный `translation_group_id`
- картинка, дата, рубрика и слаг лежат в одном месте и не дублируются
- добавление четвёртого языка — вставка строк, не миграция схемы
- легко спросить «каких переводов не хватает» одним JOIN

**Слаг общий для всех языков.** Он и так транслитерация
(`izmenil-muzh-chto-delat`), менять его по языкам — значит плодить
редиректы. Если позже захочется человеческих английских слагов,
поле `slug` добавляется в `post_translations` и перекрывает базовый.

## 4. Структура маршрутов

Сейчас маршруты лежат в `app/`. Они переезжают под `app/[locale]/`:

```
web/
  middleware.ts                    next-intl: определение языка
  i18n/
    routing.ts                     локали, дефолт, префиксы
    request.ts                     загрузка сообщений
  messages/{ru,kk,en}.json
  app/
    [locale]/
      layout.tsx
      page.tsx
      blog/page.tsx
      blog/[category]/page.tsx
      blog/[category]/[slug]/page.tsx
      kontakty/page.tsx
      individualnye-konsultacii/page.tsx
      …
    api/revalidate/route.ts        ← вне [locale], язык не нужен
    sitemap.ts  robots.ts
```

Публичные адреса при этом не меняются: `as-needed` отдаёт русский
на корне, middleware переписывает `/` → `/ru` внутренне.

`src/` (FSD) не меняется структурно — виджеты и views получают
переводы через `useTranslations` / `getTranslations`.

## 5. ISR и статическая генерация

`generateStaticParams` начинает возвращать произведение «язык × слаг»:

```ts
export async function generateStaticParams() {
  const refs = await getPostRefs()        // уже учитывает переводы
  return refs.flatMap((r) =>
    r.locales.map((locale) => ({ locale, category: r.category, slug: r.slug })),
  )
}
```

Число страниц растёт пропорционально числу переводов, не числу языков:
непереведённые статьи в чужой локали просто не существуют.

API отдаёт контент на нужном языке по заголовку или параметру:

```
GET /api/v1/posts?locale=kk
GET /api/v1/posts/{category}/{slug}?locale=kk   → 404, если перевода нет
```

На стороне DDD это не ломает ничего: `locale` становится параметром
use-case'а, репозиторий джойнит таблицу переводов. Доменная сущность
`Post` получает поле `locale` — она и так представляет «статью
на конкретном языке».

## 6. Чего НЕ переводим и что показываем при отсутствии перевода

**Правило: не показывать непереведённое.**

Если статьи нет на казахском — её нет в казахском блоге и нет
в казахском sitemap. Подстановка русского текста на казахской
странице — это дублирующий контент, за который снижают в выдаче.

| Сущность | Поведение без перевода |
|---|---|
| Статья | отсутствует в списке; прямой URL → 404 |
| Рубрика | скрыта, если в ней нет переведённых статей |
| Интерфейс | переводится полностью, иначе язык не включаем |
| Страницы услуг | переводятся полностью — это коммерческие посадочные |
| Контакты, адрес, телефон | не переводятся, но подписи — да |

Переключатель языка ведёт на **ту же страницу** на другом языке,
если перевод есть, иначе на главную этого языка — а не на 404.

## 7. hreflang

Обязателен, иначе поисковик сочтёт версии дублями.

```tsx
alternates: {
  canonical: '/blog/semja/izmenil-muzh-chto-delat/',
  languages: {
    'ru-KZ': '/blog/semja/izmenil-muzh-chto-delat/',
    'kk-KZ': '/kk/blog/semja/izmenil-muzh-chto-delat/',
    'en': '/en/blog/semja/izmenil-muzh-chto-delat/',
    'x-default': '/blog/semja/izmenil-muzh-chto-delat/',
  },
}
```

Перечисляются **только существующие** переводы. `x-default` — русский.
В `sitemap.ts` каждая запись получает `alternates.languages`.

## 8. Порядок внедрения

Разбито так, чтобы после каждого этапа сайт оставался рабочим.

### Этап 1 — каркас, без единого перевода
- `next-intl`, `middleware.ts`, `i18n/routing.ts`
- маршруты переезжают под `app/[locale]/`
- `messages/ru.json` — все строки интерфейса вынесены из кода
- **Критерий:** сайт работает ровно как сейчас, URL не изменились,
  Lighthouse не просел

### Этап 2 — интерфейс на трёх языках
- `kk.json`, `en.json` — перевод ~150 строк
- переключатель языка в шапке и подвале
- `hreflang`, `sitemap` с альтернативами
- **Критерий:** `/kk/` и `/en/` открываются, интерфейс переведён,
  контент пока русский или скрыт

### Этап 3 — контент в БД
- миграция: `post_translations`, `category_translations`
- существующие 58 статей переносятся как `locale='ru'`
- API принимает `locale`, use-case'ы и репозитории обновляются
- `generateStaticParams` по парам язык×слаг
- **Критерий:** `GET /api/v1/posts?locale=kk` отдаёт пусто,
  русский работает как раньше

### Этап 4 — наполнение
- перевод страниц услуг (6 штук, коммерческий приоритет)
- перевод статей — по одной, начиная с тех, что дают трафик
- в админке (когда ты её напишешь) — вкладки языков у статьи

## 9. Честно о цене

**Код — меньшая часть работы.** Этапы 1–3 это день-два.
Этап 4 — это перевод 220 КБ текста, то есть работа переводчика,
а не разработчика.

Машинный перевод статей по психологии **не рекомендую**:

- тема чувствительная, формулировки важны: «достаточно хорошая мать»
  в машинном переводе на казахский легко превратится в бессмыслицу
- тонкий переводной контент в больших объёмах — риск фильтра
- E-E-A-T: статьи подписаны экспертом, машинный текст под её именем
  подрывает именно то доверие, ради которого он подписан

Разумный план: **интерфейс и 6 страниц услуг переводит человек,
статьи добавляются по мере готовности.** Десять качественных статей
на казахском дадут больше, чем 58 машинных.

### Что даст казахская версия

В Мангистауской области доля казахоязычных поисковых запросов высокая,
а конкуренция в них заметно ниже русскоязычной. Это, вероятно, самая
доходная из нереализованных возможностей сайта.

### Что даст английская

Честно — мало. Англоязычная аудитория в Актау это экспаты нефтяной
отрасли, их немного. Но страница услуг на английском может сработать
на запрос «english speaking psychologist Aktau», где конкурентов нет
вообще. Делать стоит только интерфейс и услуги, блог — нет.

## 10. Решения, которые нужны от тебя

1. **Включаем английский сразу или только казахский?**
   Рекомендую: казахский полноценно, английский — только интерфейс
   и страницы услуг
2. **Кто переводит?** От этого зависит, нужна ли в админке
   работа с черновиками переводов
3. **Слаги общие или свои на каждый язык?** Рекомендую общие —
   проще и без редиректов
